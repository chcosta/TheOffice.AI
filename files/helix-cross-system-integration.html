2 The Four Repos at a Glance

dotnet-helix-machines

Role: Source of truth for queue definitions, images, and autoscale configs

Produces:

  • Azure Compute Gallery images (OS images for VMs)
  • Autoscale config blobs (autoscale/*.json, autoscale-aca/*.json)
  • Queue registry (info.json) consumed by helix-service
  • Client config (clientSettings.zip) for agent bootstrap
  • Helix client Python wheels (pip feed)
  • Matrix-of-Truth capability reports

dotnet-helix-service

Role: Core platform — job orchestration, data processing, monitoring

Contains: 25+ Service Fabric services, 21 shared libraries, SQL database, admin CLI, monitoring alerts

Key services: HelixAPI, HelixController, SqlProcessor, DeadVMCleaner, KnownIssuesProcessor, MetricsObserver, old SF-based AutoScaler actors

dotnet-autoscaler

Role: New-generation autoscaler on Azure Container Apps (replacing SF actors)

Components: AutoScaleProcessor (orchestrator), ScaleManager (VMSS ops), QuotaManager (core distribution), QueueObserver

Consumes: autoscale-aca blobs, Helix Machine API, Service Bus queue depth, Kusto historical data, Azure ARM for VMSS

arcade & helix-observer

Arcade: Helix SDK — NuGet packages for job submission (Client, JobSender, Sdk MSBuild tasks)

Observer: Monitoring dashboard — wait predictions, stuck-job detection, capacity analysis via Cosmos DB + Kusto + AzDO + App Insights

3 Shared Contracts & Integration Points

3.1 — Queue Name Format (universal identifier)

Queue names are the primary key that ties all systems together. Every repo uses the same naming convention:

{OsGroup}.{Version}.{Arch}[.Open]    e.g. Windows.VS2022.Amd64.Open
                                             Ubuntu.2204.Amd64
                                             OSX.15.Arm64
SystemUses Queue Name For
helix-machinesYAML definition file key; autoscale blob filename; VMSS naming
helix-serviceService Bus queue routing; API endpoints; queue registry lookup
autoscalerConfig key in blob storage & Redis; scaling decisions per queue
arcade SDKQueueId in job submission; queue discovery API
helix-observerCosmos partition key; wait-time tracking; capacity dashboards

3.2 — Autoscale Configuration Blob (helix-machines → autoscaler)

Storage Account: helixosauto (prod) / helixosautostaging (staging)

Container: info

Blob Paths:

  • autoscale/{queueName}.json — consumed by old SF autoscaler
  • autoscale-aca/{queueName}.json — consumed by new ACA autoscaler
{
  "QueueName": "Windows.VS2022.Amd64.Open",
  "slaInMinutes": 30,
  "SubscriptionId": "...",
  "ServiceBusNamespaceId": "...",
  "ScaleSetIds": ["..."],
  "MinCapacity": 3,
  "MaxCapacity": 200,
  "HasFixedMaxScale": true,
  "VMSize": 4,
  "CoresPerInstance": 4.0,
  "Enabled": true
}

Producer: DeployQueues.dll --scaleset-config-only (helix-machines pipeline)

Fast-path pipeline: azure-pipeline-autoscale-config.yaml updates configs without full redeploy

3.3 — Queue Registry (helix-machines → helix-service)

Artifact: info.json in management storage account

Content: Complete queue definitions with capabilities, OS, architecture, region metadata

Consumer: HelixAPI serves this via /api/2018-03-14/info/queues

Trigger: DeployQueues --update-registry=true

3.4 — Helix Machine API (helix-service ↔ autoscaler)

Base URIs:

  • Production: https://helix.dot.net
  • Staging: https://helix.int-dot.net

Endpoint: PUT/GET /api/machines/{queueId}/{machineName}/state?api-version=2019-06-17

Auth: Bearer token from Key Vault (helix-api-access-token)

Purpose: Autoscaler sets machine state (online/offline) for graceful drain before scale-down

3.5 — Image Version Format (helix-machines → Azure Compute Gallery → VMSS)

Gallery Image Names: Helix-{OS}-{Version}-{Date} (e.g., Helix-Ubuntu-2204-2025-11-12)

Version Format: YYYY.MMDD.HHMMSS (e.g., 2024.0520.063705)

Defined in: Queue YAML definitions under GalleryImage.Name + GalleryImage.Version

Flow: helix-machines pipeline → Azure Compute Gallery → VMSS model references → autoscaler scales instances

  • Manages VMSS via ARM templates
