No duplicates. Each work item gets at most one auto-created card — matched by org/project/#id. Cards you created by hand, or that already exist for that work item, are never touched. Polling runs on a single leader instance, so multiple open windows won’t double-create.

Today a dev card writes one focused implementer agent into its worktree. This makes it a roster: pick from playbook personas, add as many as you want, at any time. Each writes its own .github/agents/<name>.agent.md into the worktree — selectable in VS Code / Copilot, auto-selected in the CLI.

Goal

Produce a short design brief for the fix — the approach, alternatives considered, risks, and a recommendation — before implementation begins.

How it works

  1. Read the work item and the relevant subsystem.
  2. Draft 1–2 candidate approaches with trade-offs.
  3. Call out risks, blast radius, and what to measure.
  4. Recommend one and note open questions for sign-off.

Guardrails

  1. Read-only — design only, no code changes.

Goal

Independently verify the change is correct and the wait-time win is real and repeatable — not just plausible.

How it works

  1. Identify what “done well” means and how to measure it.
  2. Write/extend tests that capture the behavior + edge cases.
  3. Run the baseline and after measurements the same way twice.
  4. Report pass/fail with the quantified delta.

Guardrails

  1. Don’t modify product code to make a test pass — flag it.
